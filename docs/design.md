# Design

This document describes the implemented extension, not a roadmap. Its evidence is the checked-in code, public package contracts and reproducible tests. DbgX package availability does not establish a Microsoft support or API stability guarantee.

## Ownership and dependency boundaries

| Component | Owns | Must not own |
| --- | --- | --- |
| Bootstrap | MEF exports, titled/persisted tool window, native ribbon, UI activation | SDK sessions or WebView2 dependencies in the host load context |
| WinDbgChatView | WebView2 bridge, theme, authentication console, debugger adapter | Hidden host-member introspection or a second chat state machine |
| ChatCore | SDK session lifecycle, approvals, tool activity, usage, history | WPF or DbgX types |
| Contracts | Cross-context interfaces and versioned bridge DTOs | SDK or UI dependency types |
| web | React rendering, composer, rich content and explicit speech playback | Credentials or direct debugger access |

The bootstrap and shared contracts are the only root assemblies. UI/WebView2 and SDK dependencies live in separate directories and separate `AssemblyLoadContext` instances. Sharing contract, WPF and DbgX assemblies preserves type identity across the host boundary; loading a second copy of a contract would make otherwise identical-looking types incompatible. Tests check those identities and that bootstrap does not reference the UI/WebView2 assemblies. The contexts are non-collectible: disposing chat resources is not a promise to unload assemblies. Restart WinDbg after replacing binaries.

The tool-window and ribbon exports are separate MEF parts because both metadata attributes contribute `Name`; combining them produces duplicate metadata. Tests compose the exports through a `TypeCatalog`, not only direct constructors. Both the normal view and load-error view use a titled `ToolWindowView`. Failed UI activation is not cached, allowing a subsequent open to retry. Persisted export identifiers must remain stable across upgrades.

## Transport and trust

Production web assets are mapped to `https://copilot-chat.invalid/index.html` inside WebView2. There is no application HTTP listener. This reduces the deployment surface but does not eliminate the need to validate messages: the native bridge checks the exact document source, protocol version, request identity, session, payload sizes and replayed request IDs. Native state remains authoritative.

The WebView blocks external navigation, frames, downloads and unused permissions. Markdown disables raw HTML and remote images; only explicit raster attachments are previewed. Mermaid uses strict mode and sanitized SVG. HTML labels are disabled because sanitization removes `foreignObject`; enabling them can silently remove diagram labels. Browser tests assert label visibility as well as rejecting unsafe content. Links are inert until clicked.

The browser demo uses synthetic state. It cannot discover a live debugger or authenticate. Development Vite servers are not part of the installed extension.

## Debugger operations and consent

All engine operations are serialized through the adapter semaphore and posted to `IDbgEngineSynchronizationContextSource.SyncContext`. A WPF dispatcher is not a substitute for the debugger context. `IDbgConsole.ExecuteCommandAsync` completion, rather than an SDK notification, determines when output capture ends and the execution gate can be released.

| Operation | Consent | Result destination |
| --- | --- | --- |
| AI `debugger_target` | Automatic read-only property query; no debugger command | Copilot |
| AI `debugger_command`, Ask mode | Separate execution and output-sharing approvals | Local activity first; Copilot only after sharing approval |
| AI `debugger_command`, Approve all | Explicit mode authorizes execution and sharing, including pending approvals | Local activity and Copilot |
| Clicked command link | The click authorizes current-target execution without another prompt | WinDbg only |

Approvals are one-use and tied to the displayed command or output. Immediately before execution, the adapter confirms that a stopped target exists; WinDbg then owns command behavior if the active target changes. The extension deliberately does not subscribe to target lifecycle events or cancel the chat turn when the active target changes. Real-host command failure behavior and manual-console output interleaving require smoke tests.

Cancelling chat denies pending approvals and suppresses stale results. It does not interrupt an already-running debugger command. The adapter retains its gate until that command returns, and turn cleanup awaits outstanding tool tasks. Releasing either early could mix output or execute conflicting work.

SDK callbacks and progress events can arrive in different orders. `CopilotTool.DefineTool` binds `ToolInvocation` outside model-supplied arguments; its `ToolCallId` identifies a single activity across start, local output, sharing and completion. Late events must not duplicate or reopen completed activities. Tests invoke the SDK function with simulated context and verify withheld output is absent from the returned SDK result.

Debugger commands are not sandboxed: they may write files, load extensions, launch code or cause network activity. Denying output sharing cannot undo effects of a command already executed. Full output is memory-resident; there is no extension-side truncation, and SDK context limits still apply.

## Tool selection and MCP configuration

The host reads MCP JSON files through `ToolConfiguration`; the web bridge receives only tool names/descriptions, server status and the configuration path. Open mcp.json uses the active host-owned path or the extension's default local application data path, never a path supplied by the web client. Missing files are created with an empty `servers` object without overwriting existing content, then opened through the Windows shell file association. Opening does not parse or reconnect; Reload tools applies saved changes, including a newly created default file. VS Code `servers` and SDK `mcpServers` formats are translated into typed SDK stdio/HTTP configurations. Environment placeholders are expanded locally. Unsupported interactive variables and env files fail explicitly rather than being passed through to commands.

Tool preferences are global to this Windows profile's extension, not saved in individual conversations. Only WinDbg tools start selected. Built-ins and MCP tools come from the session's initialized current-tool metadata, not the generic `server.tools.list` catalog. This accounts for model/runtime settings; model changes refresh the catalog too. Host policy excludes disabled skills and unimplemented question/answer and subagent flows. Shell and file search/edit tools remain eligible when initialized by the session; their names are not inferred from the OS. These exclusions do not apply to MCP tool names. Catalog replacement also intersects the active selection with the eligible tool IDs so hidden tools cannot remain enabled.

Explicitly enabled MCP servers are configured at session create/resume; initialization and current-tool metadata supply their canonical execution names rather than constructing names from strings. Discovery temporarily broadens the SDK list using `ToolSet().AddBuiltIn("*").AddMcp("*").AddCustom("*")` while holding the lifecycle gate, with no user turn running and the pre-tool hook denying execution, then restores the selected allowlist in `finally`. A bare `*` is not a valid SDK filter. Failed discovery or allowlist restoration blocks sending until successful rediscovery. These RPCs are experimental in SDK 1.0.4 and need version-specific live verification. Metadata availability does not prove execution dependencies or permissions are satisfied.

Tool-only changes use `session.options.update`. MCP connection/configuration changes dispose and recreate/resume the same SDK session, preserving UI history, usage, identity, model and approval mode. Empty sessions use create; conversations use resume. Configuration changes are serialized with send/model/session operations and rejected during an active turn. Failure blocks new sends until a successful reload. New MCP connections require native trust confirmation; saved enabled connections are trusted again on startup/reload.

The pre-tool hook denies unselected, stale, cancelled and out-of-turn calls. WinDbg retains its existing command/output gates; other selected calls use a pre-execution consent covering both action and returned data. SDK permission callbacks are also routed through the approval gate. Cancellation returns denial rather than throwing from a hook. Approve all resolves these requests automatically. This is not a process/network sandbox: starting an MCP server itself can have side effects and approved non-debugger results have no separate output-withholding step.

## Authentication and session lifecycle

MCP connection-status and OAuth-required events are processed even while no user turn is running. Only current-session events for enabled, configured servers update the picker. Connection generations reject events from a previous SDK session even when the conversation ID is reused; reconnect resets status to pending. Status notifications received during an in-flight MCP list request take precedence over its older snapshot, so `needs-auth` cannot be overwritten by stale `pending`. A transition to `connected` queues a serialized tool/status refresh, deferred during active turns. Duplicate connected notifications do not queue another refresh. Discovery restores the selected allowlist before new sends are allowed and never selects newly discovered tools. Notifications do not open a browser; Reload tools remains a manual retry.

MCP OAuth is user-initiated for enabled HTTP servers through `session.Rpc.Mcp.Oauth.LoginAsync`. A native confirmation precedes the request; returned browser URLs must be HTTPS without embedded credentials and their authority is confirmed before shell launch. Only the server name and command type cross from the web UI. Normal Sign in requires `needs-auth`; Sign in again is available for any enabled HTTP server and passes `forceReauth: true` only after a separate confirmation explaining cached-token removal. It sets pending before initiation so completion triggers a refresh even when the previous status was connected. The SDK handles the callback and tokens, using persistent OS keychain storage; no token or authorization URL crosses back to JavaScript. Sign-in initiation has a 60-second RPC cancellation timeout. Browser completion remains SDK-owned; its connection notification triggers metadata refresh. Disconnecting is not credential revocation; browser cookies and configured headers are not cleared by reauthentication.

Initial discovery checks `session.Rpc.Mcp.ListToolsAsync` for each connected, enabled server (30-second timeout per call), in addition to initialized session metadata. Comparison respects configured per-server tool filters. If the two catalogs disagree, only the affected connections are disabled/enabled once before reinitialization; reinitialization alone and `Mcp.ReloadAsync` did not clear the empty initial cache in the local SDK probe. Persistent mismatches and tool-list rejection block sends with a diagnostic while retaining manual reload and reauthentication. A successful empty tool-list response is reported separately. Recovery does not manufacture canonical tool IDs or enable newly discovered tools, and the selected allowlist is restored on success and failure.

The UI requests one connection after startup, including under React effect replay. It uses saved CLI authentication and never starts interactive OAuth automatically. A failure requires manual retry. Each successful connection starts a fresh session with the previous model; old conversations are resumed only through History. New and resumed sessions default to Ask mode.

The SDK child process inherits the Windows environment except the three token overrides intentionally cleared for CLI-selected login. Replacing the entire environment can break native process initialization. SDK 1.0.13 bundles a dedicated runtime under the compatibility name `copilot.exe`; it rejects interactive CLI flags, so startup does not pass `--disable-builtin-mcps` or `--no-custom-instructions`. Session configuration still explicitly controls MCP servers and disables configuration discovery and custom instructions.

Initial sign-in and account switching share the native `signIn` handler, dispatched before the session-existence check. The UI offers Sign in when unauthenticated or account status is unknown, and Switch account when authenticated; native confirmation text follows the same distinction. Both use an installed official Copilot CLI in a visible PowerShell console, with its absolute path passed as an environment value rather than interpolated script text. Discovery checks absolute process/user/machine PATH entries and Windows WinGet/WindowsApps links, not the current directory. If absent, native confirmation offers `winget install --id GitHub.Copilot --exact --source winget --scope user` without elevation or automatic agreement acceptance. Installation/lookup happens before disconnecting any current chat; PATH is read again afterward. Missing winget, failed installation or a CLI that remains undiscoverable produces actionable errors. Converting forwarded output items to text avoids PowerShell error-record decoration while preserving diagnostics and exit codes. Tests cover lookup, installer arguments, paths with spaces/metacharacters and simulated success/failure; no OAuth output enters the bridge or test logs.

The extension keeps a UI history record separately from SDK session storage. An empty local record does not imply an SDK session can be resumed; submitted conversations use resume, while empty ones use creation. SDK title events update automatic titles, but manual names take precedence. Switching accounts does not isolate history on the same Windows profile.

History includes local tool output even when sharing was denied, plus attachment preview bytes. It is not additionally encrypted. Atomic replacement and a 64 MiB limit protect file integrity, not confidentiality. Save failures are reported without trimming data; an interrupted turn may not have been saved. Uninstall retains local history and credentials.

## Rendering and reported data

Usage and model prices come from SDK telemetry. A model cost multiplier is not a credit charge; absent data stays unknown or partial. Displayed session totals are not an account billing statement. Late usage belongs to the session subtotal rather than inventing a completed-turn attribution.

Speech uses a matching local voice by default. Right-clicking a read-aloud button opens the runtime's voice list; selecting a voice stores its `voiceURI` and uses that exact voice until Automatic is selected or the voice becomes unavailable. Selecting a voice advertised as `localService=false` may send read-aloud text to the operating-system voice provider. Speech never autoplays, and playback identity guards reject late callbacks from prior utterances. Runtime-reported locality does not independently prove network behavior; mock tests cannot establish installed Japanese or online voice availability.

Completed assistant responses can be opened as large-format reports either in the default browser or directly in Microsoft Edge Immersive Reader. The native bridge renders Markdown with raw HTML disabled into semantic content under `article#immersive-reader-content`, adds document/content language metadata and applies a restrictive CSP. Mermaid SVGs already sanitized and rendered by the web UI are sent separately and checked again by the native host. The validated SVG bytes are embedded as `data:image/svg+xml` image sources rather than inline SVG elements: scaling remains vector-based, while reader mode treats each diagram as one image instead of reconstructing its internal text and geometry. Code and call stacks remain HTML text so they can be selected and copied in either report mode. Edge exposes no documented per-element Read Aloud exclusion attribute; the Immersive Reader report therefore adds only the standard `aria-hidden="true"` hint to generated `pre` elements, without removing or replacing their visible content. Edge may vary in whether its built-in Read Aloud honors that metadata. Diagram image isolation requires the CSP's narrowly scoped `img-src data:`. An in-process TCP listener bound explicitly to `127.0.0.1` serves each report at a random 256-bit path, requires the exact loopback `Host`, accepts only `GET`, and returns `no-store`, `nosniff`, frame-denial, no-referrer and restrictive CSP headers. Normal opening shell-executes the HTTP URL; Immersive Reader opening finds an installed Edge executable and passes the official `read:http://...` form as one argument. Reports remain only in memory for up to one hour, are capped at 32 entries, and are cleared when WinDbg exits. The semantic container follows the Azure Immersive Reader SDK's input guidance, while the `read:` launch uses Edge's separate built-in feature and does not invoke the Azure service.

## Maintenance

- Keep packaging layout and shared assembly identities covered when changing dependencies.
- Test event permutations and delayed debugger completion, not only the successful synchronous path.
- Keep authentication, debug-target access and installation out of ordinary CI.
- Revalidate host compatibility when updating DbgX, WebView2 or Fluent.Ribbon; do not copy host implementation details into tests.
- Keep release evidence with each candidate; see [Validation](validation.md). Preserve useful rationale here instead of retaining superseded implementation plans.
